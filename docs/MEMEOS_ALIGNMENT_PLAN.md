## 1. 产品目标：为什么用户要在 pons 之外使用 MemeHelm

MemeHelm 为英文用户提供贯穿“准备项目 → 发币 → 管理社区 → 理解链上变化 → 复盘运营结果 → 管理收入”的工作台。

pons 承担发行、曲线交易和毕业池基础设施；MemeHelm 的增量价值是项目上下文、MATE 运营协助、可追溯的链上研究、社区流程和清楚的收入管理。增强计划应让这些流程衔接起来，而不是只增加更多导航入口。

| 用户问题 | 产品应提供的结果 |
| --- | --- |
| 我还没有项目，该准备什么？ | 无项目也能与 MATE 讨论平台相关的想法；用户确认后再建立真实项目记录。 |
| 我为什么这样设置发币参数？ | 解释实际可选配置、费用、收款地址和规则边界，并在签名前重新核实。 |
| 发币后今天该做什么？ | 基于项目目标、已观察事实和上次结果，形成可审核的下一步。 |
| 持有人和创建者发生了什么变化？ | 提供有来源、时间和覆盖范围的证据，逐步加入资金关系图。 |
| 内容和活动做完了吗？ | 区分私人草稿、已审核、已公开、已完成和实际结果。 |
| 收入在哪里，谁能领取？ | 解释协议待结算费用、escrow 余额、金库到账与付款记录，准备可核对的交易。 |

### 当前验收边界

- 已有本地自动化与主网分叉验证记录；不把历史测试数量当作未来版本的永久保证。每个交付版本重新记录提交号、命令、环境和结果。
- 主网分叉中的本地交易不是主网广播；模拟成功不是独立审计。

- X 发布有代码和模拟供应商测试，尚无真实账号验收。没有开发者应用凭证时，手工发布路径可以继续完成。
- 本地工作区还不能代表已提供公网服务。服务器与域名尚待用户提供。

## 3. 范围与协议兼容性

### 继续执行的产品边界

1. 保持 Robinhood 主网与 pons v2，不恢复旧发行协议或独立发行工厂；产品不增加测试网模式。本地模拟和分叉仍用于验证。
2. 服务器不保管用户交易私钥。每笔资金交易由用户钱包明确签名；SIWE 登录不授予花费权限。
3. 自动观察、付费 AI 复盘、私人提案、内容公开、X 发布和资金执行是不同权限，不能用一个“开启 AI”全部授权。
4. 保留明确排除的范围：自主做市及 3M 类机器人、跨链发行。
5. 产品文案为英文，时间统一 UTC。开发进度、密钥和配置只出现在内部文档。

### 不实施原稿中的直接移植

**自定义 Sentinel。** 当前 pons 发行接口没有自定义代币实现或 Hook 参数；其毕业池使用共享 Hook。v4 Hook 在池创建时确定，Swap Hook 也不覆盖普通 ERC-20 转账。因此，不能把新增 Sentinel 合约包装成现有 pons 发行选项。保留实际协议规则展示；更改发行协议需要单独决策。[pons v2 官方文档](https://docs.ponsfamily.com/v2)、[Uniswap Hook 文档](https://developers.uniswap.org/docs/protocols/v4/concepts/hooks)。本地详细评估见 [Sentinel 兼容性](SENTINEL_PONS_INTEGRATION.md)。

**CA Vault。** 自定义地址属于辅助工具，不是新增发行模式。pons 已有基于发起地址、发行参数和 salt 的确定性地址机制；如未来开发靓号工具，必须针对最终参数预测并确认，不能承诺同一预挖地址可任意换钱包或元数据使用。[pons 确定性发行地址说明](https://docs.ponsfamily.com/v2)。本期不把靓号工具放进核心交付。

**服务器子钱包。** 加密保存私钥仍意味着服务器能签名；Redis 中的预算不能在密钥泄露后强制限制花费。本期不开发这一托管模型。未来如评估自动交易，应先决定是否采用支持链上限额、合约/方法白名单、期限及撤销的授权账户，再做威胁模型与兼容性验证；这不是当前已存在的能力。

**社交认领与持币奖励。** 当前 SocialVault 是控制人提案、两天等待和执行模型，不是凭 X 身份直接认领；当前 HoldersVault 是审核后批次付款，不等于 MEME OS 的完整 Counter 机制。沿用准确名称，分别展示其真实保证。

### 待单独决策，不计入本轮完成条件

Quant 自动交易/跟单、OTC 合约、无需逐条审核的 X 自动发布、X 身份链上认领、Merkle 奖励新合约、平台币发行/质押/回购、平台抽成。除已明确排除的自主做市和跨链发行外，其余是暂缓建议，不替用户永久取消。

## 4. 实施顺序与发布单元

不预设“四周全部完成”。以下阶段按依赖推进；每个阶段先完成一个可演示的用户流程，再扩展。工作量、外部服务能力和合约安全要求核实后，才能给时间承诺。

| 阶段 | 优先级 | 交付结果 | 前置依赖 |
| --- | --- | --- | --- |
| A 核心闭环与数据准确性 | P0 | 新用户、发币、MATE、社区和收入流程有可重复验收；先处理误导性付款描述 | 当前正式代码与可运行本地环境 |
| B 链上研究与 Visualizer | P1 | 更可靠的历史覆盖、早期买家和可点击的资金关系证据 | A 的覆盖字段规范；RPC/索引服务能力核验 |
| C MATE 运营与社区结果 | P1 | 观察 → 复盘 → 私人提案 → 审核 → 执行/记录 → 下一次复盘 | A 的状态与幂等验收；B 的新证据可以逐步接入 |
| D 收入与持币分配增强 | P1 | 可核对来源、分母、名单、金额与付款记录 | A 的样本披露；完整分红模式依赖 B 的快照能力 |
| E 首版生产准备与上线验收 | P0 发布门槛 | 可备份、恢复、监控和安全访问的单实例服务 | 准备工作可提前并行；实际上线依赖用户部署环境 |
| F Developer API | P2，可选 | 对外只读研究接口、作用域 Key 和可追踪额度 | 稳定的数据与生产服务、真实外部使用需求 |

P0 是在对应功能正式交付前必须处理的门槛，不表示 B–D 开发期间要提前公开部署。

## 5. 阶段 A：先把现有产品验收清楚

### A1. 发布基线与工程可读性

- 建立“正式功能 / 本地验证 / 外部待验收 / 待开发”清单，入口均指向真实页面与记录。
- 以正式提交的干净快照构建和测试；不混入本地未跟踪的独立发行试验。保留用户本地试验文件，不为清理发布而擅自删除。
- 如需要格式化，只分批整理直接涉及的模块；格式变更与行为变更分开。先建立回归再拆 `server/index.mjs` 路由，不做全仓一次性重写。
- 不为格式化预先引入数据库、队列或 UI 大库。依赖新增必须对应确定的交付需要。

### A2. 五条用户路径

| 路径 | 必须能演示的成功与异常行为 |
| --- | --- |
| 首次入站 | 5.5 秒 MATE 入场、跳过、减少动态效果、移动端；未登录可以浏览，登录后无项目聊天；无关问题被拒答。 |
| 发币与交易 | 必填项、图片预览/有效托管链接、草稿恢复、实时权限/费用、精确收款人、模拟、签名拒绝、报价过期、网络/账号切换、待确认与回执恢复。 |
| AI 运营 | 新建私人提案、编辑、驳回/批准、结果导航、记录实际结果、下一轮复盘引用；超时重试不得重复计费或重复建记录。 |
| 内容与社区 | 私人日历、活动发布/隐藏、报名/容量/取消、手工 X 发布记录；明确“计划时间”不等于自动发文。 |
| 收入 | 费用结算、escrow 收取、付款准备/取消/恢复、空余额和索引不可用；准确展示金额归属与控制权。 |

发币、交易和付款先以本地分叉、模拟和测试钱包界面演示。真人主网验收由用户自主确认并签名，不能因本计划存在而由代理广播。

### A3. 优先修正持币分配的语义

现有算法按接口返回样本中的余额计算份额，无法从缺失地址推导“全体持有人”的权利。**不能声称样本外持有人的应得份额已经留在金库。** 只有已经计算后因门槛、人数上限或明确排除而未支付的份额，才可说明为留存。

短期保留明确标注的人工样本批次：显示返回地址范围、计算分母、排除项和本轮收款人，说明样本外地址本轮不收款，并要求单独确认。没有有效持仓数据时不能准备付款。完整分红模式在阶段 D 达到数据要求后再开放，不删除现有金库页面或隐藏限制。

### A 验收门槛

- 所有核心路径都有成功、空、失败、超时和重试状态；页面没有无期限读条。
- 另一个钱包不能读写私人项目、聊天、提案、发布队列和付款准备。
- 浏览器取消签名、发送结果不确定或进程重启后，不自动重发资金交易、X 帖子或已开始的付费 AI 请求。
- `pnpm check`、相关合约测试及适用分叉检查有真实结果；未运行的项目列为未验收。
- 真浏览器检查桌面、平板、手机、键盘焦点、弹窗、未保存内容和跨页面状态，至少两轮截图检查并记录修正。

## 6. 阶段 B：链上研究与资金关系图

### B1. 先建立可恢复索引

复用 `server/market.mjs`、`server/token-research.mjs`、`server/pons.mjs` 与现有数据库接口。需要时新增索引模块，不用新文件名替代已有能力。

- 按已验证的 factory、curve、hook 和 escrow 来源索引事件；历史协议栈与当前部署分开，不给未支持的工厂套用当前保证。
- 保存起止区块、区块哈希、游标、缺失范围、最后成功时间和归一化事件。唯一键至少包含链、交易哈希、日志索引；来源栈单独记录。
- 实时订阅只是加速途径。断线、RPC 限流、进程重启都要能按区块范围补读；不承诺毫秒级发现或已经覆盖全链历史。
- 对未确认区块标记暂定状态；根据链与服务商能力确定确认策略。检测到重组时回滚孤块派生数据并重放，不能只覆盖最终游标。
- 同一批事件及游标用事务写入；失败不得推进游标。设限速、批大小、缓存、积压可见状态和总请求上限。

### B2. 逐步增加研究能力

1. **早期买家**：仅在覆盖已核实的发行起点且期间无缺块时展示“最早 N 笔”。否则叫“当前覆盖内的买入”，不能把最近 50 笔当成创世买单。
2. **创建者历史**：在持久化索引上扩展已有记录；标出覆盖工厂、日期和区块，不把近期无记录写成从未发币。
3. **资金来源关系**：对限定地址数、时间范围和深度建立有向图。边保留交易哈希、金额、资产、时间、来源与关系类型；普通转账和内部调用分别标记，拿不到 trace 就说明没有覆盖内部资金流。
4. **公共服务过滤**：交易所、桥、路由器等地址如有可验证标签，保留标签来源和版本；未知不能默认算私人母钱包。
5. **Visualizer**：先交付有限规模可交互关系图，点击节点或边可查看证据并回到研究详情；手机提供列表替代，不能只交付装饰性气泡。

共用资金来源不等于同一控制人。首版展示关系与证据覆盖，不输出未经校验的“庄家/捆绑盘”结论或 0–100 安全分。研究结论不得承诺不会亏损。

### B 验收门槛

- 重复日志、乱序日志、断线、分段失败、重启和重组不会产生重复或错误的事实。
- 历史不全、RPC 无历史/trace、公共地址误归类均有测试；缺失数据不会被表示为安全通过。
- 图上的每一条事实关系能定位到证据；没有证据的关系不画成确定边。
- 新数据缺失不会阻塞现有价格、交易和项目页面，也不覆盖最后成功结果。
- 前端有来源、UTC 时间、区块范围、索引进度与局限说明；实现状态进入内部记录，产品只显示用户需要的数据新鲜度。

## 7. 阶段 C：把 MATE 做成持续运营助手

复用 `operations`、`copilot`、`assistant-actions`、`request-journal`、内容日历和社区模块。能力增强以可追踪的行动与结果为中心，不新造一个能任意调用合约的通用 Agent。

### C1. 三种清晰权限

| 层级 | 允许的行为 | 不随之授予的权限 |
| --- | --- | --- |
| 观察 | 按用户设置读取链上变化、产生事实观察 | 不调用付费 AI、不发布、不签名。 |
| AI 复盘 | 用户显式启用后，按频率和 UTC 日请求额度生成私人分析/提案 | 不自动公开内容，不授予资金预算；请求次数不伪装成美元或 ETH 预算。 |
| 审核与执行 | 用户检查提案，创建私人内容/活动，或打开现有付款审核；后续按各自流程确认 | 内容批准不等于 X 发布；付款提案不包含模型选择的 calldata 或收款人。 |

保留默认关闭的调度。暂停、额度耗尽、权限或上下文变化时按规则停止/作废在途结果；不得把缺失观察编造成事件。中断的付费调用要先查看已保存工作，再由用户决定是否发起新的请求。

### C2. 用户看到的运营闭环

- 项目 Overview 汇总“发生了什么、正在做什么、接下来可以做什么”，每项能跳到其记录；无项目状态用真实可操作的开始流程，不填假项目、假余额或假 AI 回复。
- 每个建议显示依据、观察时间、局限、建议行动与待审核状态。人工填写结果和链上/X 验证结果分开标识。
- 私人内容、活动和任务之间保留提案来源及目标记录；编辑后的内容回到待审，不复用旧批准。
- 复盘使用过去行动的实际结果；生成计划、保存草稿、发布和达成效果分别记账，不互相冒充。
- 无项目聊天继续可用；需要项目的动作给清楚的下一步，不能通过后台生成假项目绕过权限。
- 保留服务器平台范围校验与输出验证。链上元数据、网站文字、用户上下文和工具结果不能改变助手权限；拒答策略需要持续回归，不宣称绝对抗越狱。

### C3. 社区先完成不依赖 X 开发者账号的路径

先验收“草稿 → 审核 → 在 X 打开 → 用户自行发布 → 记录链接和结果”。手工结果标为创作者报告，未验证的互动数据不冒充 API 读取，未知值保持未知。

取得真实 X 应用凭证后，再验收已有 OAuth 路径：连接/刷新/断开、当前账号、逐稿批准、发布确认、回执及结果读取。编辑、换号或连接更新使旧批准失效；发送结果不确定时禁止自动重发。本期不增加无人审核的自动发推。

### C 验收门槛

- 只开观察时供应商调用数为零；定时 AI 仅在明确启用、额度充足且服务可用时运行。
- 同一请求重放不重复计费或建提案；同一提案重复应用不重复建活动/内容。
- 修改后的内容与账号不能沿用旧批准；私人记录不因完成任务而自动公开。
- 一条完整结果能被下一次复盘引用，且仍带原始来源和验证状态。
- 跨钱包、跨项目、无关提问、上下文指令注入、超时和暂停均有回归用例。

## 8. 阶段 D：收入、持币分配与托管透明度

### D1. 收入账目与恢复

- 保留现有 `sweep → escrow claim → release / distribute / propose / execute` 流程，统一清楚的步骤和回执。
- 协议未结算 gross fee、收款地址的 escrow 余额、金库到账和已支付分别显示。一个收款地址覆盖多个代币时，不把地址总余额归属为单个代币的收入。
- 需要协议运营方处理的兑换或回购保持等待状态，不提供一定会成功的“全部领取”。
- 每次准备重新核实链、协议栈、金库类型、控制人、余额、轮次与模拟；展示实际收款人、金额和有效期，最终由用户钱包签名。
- 页面重载或回执丢失后先读链上事实，不能凭按钮点击记录成功，也不能自动重发。

### D2. 完整分配模式的条件

增强审核数据模型：`source`、`checkedAt`、`snapshotBlock`、`snapshotBlockHash`、`paginationComplete`、`coverage`、余额集合、计算分母、排除规则、舍入与留存。

- `snapshotBlock` 未知就保留未知。只有同一已确认区块的完整余额集合及可解释的供应量核对，才可标记 `complete`；仅地址数量等于接口 holdersCount 不构成证明。
- 核验 RPC/索引服务是否支持固定区块、完整分页及必要历史读取。当前余额 API 的读取时间不能冒充固定区块。
- 完整条件不具备时，仅保留阶段 A 明示的样本批次，或拒绝准备；不得悄悄归一为全体持有人份额。
- 名单、金额、计算版本和证据摘要在审核时冻结。名单变化、过期、余额不足、轮次变化、快照块重组或模拟失败均需重新审核，不静默换数据。
- 当前合约只执行控制人提交的名单，不在链上验证快照。即使后端索引更完整，也不能宣传成无需信任的自动奖励。

Merkle 领取或链上快照承诺属于新合约版本与新部署，需单独设计和安全评估。不得声称现有不可升级金库能原地获得这项保证。

### D3. 社区托管

继续展示控制人、实际两天等待窗口、提案、取消、执行和资金占用。X 连接不是准备或执行托管付款的条件；授权来自控制钱包。OAuth 既不是链上 X 身份证明，也不能代表社区批准或赋予社区否决权。

如果以后决定做 X 身份认领，另立方案评估不可变 X 用户 ID、认领钱包绑定、签名域、nonce、期限、重放防护、账号更名/接管、验证者权限与恢复政策。单独增加 EIP-712 签名不能解决全部身份信任问题。

### D 验收门槛

- 重复/缺失分页、重复地址、未知块号、样本分母、门槛、超过 200 人和显式排除有确定预期。
- 失败收款方、重入、错误控制人、错误链、费用归属、余额/轮次变化和回执恢复通过相应测试。
- 审核显示名单与实际 calldata 一致；样本外、排除项、舍入和未付金额的说明与算法一致。
- 所有资金写入仍在用户钱包完成；MATE、观察定时器和内容批准均不能出款。

## 9. 阶段 E：先做可维护的单实例生产版本

生产准备可以并行进行，但实际公网部署仍等待用户提供环境；不能直接把现有本地端口暴露出去充当上线。

### E1. 当前架构上需要补齐的工程工作

- 继续使用 SQLite 的前提是单个 Node 应用实例、单一调度者、持久化本地卷、可接受的数据规模与实测延迟；首版不承诺共享网络文件系统或多活。当前是 SQLite 中的 JSON 文档集合存储，交易原子性已存在，但整集合读写不是无限可扩展的关系查询。
- 给认证、业务存储和后台任务提供清楚的存储边界。先做带版本的 schema 迁移；高频索引和任务记录可用独立关系表，不把全部业务一次重写。
- 首版可明确接受“服务重启后重新签名登录”，无需仅为保持登录引入 Redis；若要求重启保持登录，再持久化带过期和撤销的会话。持久化时数据库只存 session token 摘要；challenge/登录 nonce 一次性消费，过期与退出仍有效。需要恢复的任务和用量记录必须持久化。
- 明确部署 origin、允许 Host、代理信任边界、HTTPS、Cookie 和写请求来源策略。已有 Origin、JSON 和 SameSite 保护须保留；补齐缺失 Origin、`Origin: null`、同站不同来源及可信代理的生产策略与测试，不能仅凭缺失 Origin 分支断言存在可利用漏洞。不直接删除 localhost 限制后发布；登录 challenge/verify 另设可信来源限流。
- AI 请求日志继续提供幂等与用量证据。补充任务运行账本、租约/恢复和唯一约束，但不让恢复队列重新发送不确定的付费请求、帖子或交易。
- 使用支持 SQLite 一致性的备份方式，覆盖 WAL 处理、备份加密/保留和恢复演练；不能把正在运行的单个 db 文件随手复制当作完整备份。
- 监控服务健康、磁盘、数据库错误、索引落后、RPC 失败和 AI/X 失败。日志不记录私钥、会话明文、供应商密钥或私人聊天全文。
- 提供数据导出、保留/清理策略与私人数据删除流程；说明已经上链或发往外部平台的内容不能由删除本地记录撤回。包含当前访问者报名等个人状态的公共响应保留 `no-store`，不得直接放入全站共享 CDN 缓存。

### E2. PostgreSQL / Redis 的引入条件

出现多个写入实例、数据库锁竞争/集合读写成为实测瓶颈、多个 worker 需要共享状态或明确的运维要求时，再设计迁移。

- PostgreSQL 可承担结构化业务、索引与任务事务；Redis 可承担共享限流、短期缓存或协调，二者不是完成多租户隔离的替代品。
- 数据库迁移保留所有权、chainId、revision、请求身份、历史回执和时间语义。先验证备份/回滚、计数和记录一致性，再切换写入路径。
- Redis 锁不替代数据库唯一约束，也不构成钱包资金支出限制。过期、故障和分区时需定义行为，不能只加入一个锁就宣称可水平扩展。
- 不把私人工作区迁移当成自动公开项目页面的授权。

### E 验收门槛

- 用隔离的生产配置验证登录、过期、退出、声明的重启会话行为、任务/用量恢复、跨钱包隔离和跨站拒绝；受信代理和错误 Host/Origin 均有用例。
- 完成备份恢复演练，并从恢复数据继续读取私人项目、提案、任务与请求日志。
- 用声明的负载目标测试吞吐、内存、数据库等待和后台任务积压；没有实测前不宣称支持大规模并发。
- 真实域名 HTTPS、供应商凭证、真实 X 连接及真人主网流程分别记录验收状态，不能用本地测试结果顶替。未接入真实 X 时可以仅交付明确标注的手工路径，不把 API 发布伪装成可用，也不把可选 X 集成当成全部产品上线的必要条件。
- 钱包确认前的金额/地址与签名请求一致，所有公开页面仅含明确批准的字段。

## 10. 阶段 F：有需求再产品化 Developer API

先复用稳定的市场/研究读取能力，建议首版仅开放只读接口。候选资源为 token facts、trades、research 与 coverage；最终路径和版本作为接口设计产出，不伪装成已经存在的 endpoint。

计划要求：Key 仅保存摘要、作用域、创建/撤销、每分钟限额、按 owner 的使用记录、响应版本、错误与额度规则。私人项目数据默认不对第三方 Key 开放。

付费计费另设原子用量账本、幂等计费和失败处理；先完成计量，再决定免费额度/价格。不预设平台币或强制销毁机制。

API Key 不拥有交易签名权。如未来提供交易准备接口，只返回经校验的未签名交易，并独立设计权限与限额；不加入服务器代客执行的 `/trade/swap`。

MEME OS 的公开 Developer API 可参考其 Key、额度和文档组织，但其接口并不证明 MemeHelm 已具备同等后端或应直接照搬收费模型。[官方开发者页面](https://memeos.world/developers)。

验收覆盖 Key 越权、撤销、额度并发、错误计数、分页、稳定响应结构和私人信息泄露；文档示例不得包含真实凭证。

### 候选数据记录

这些是逻辑记录，不是已建表的声明，也不要求立即上 PostgreSQL。

- **身份**：challenge、session 摘要、owner、chainId、过期/撤销；用户档案不等于会话表。
- **索引**：chainId、协议栈、区块号/哈希、交易/日志、游标、缺口和重组状态；事件唯一键和查询索引明确。
- **证据与快照**：来源、获取时间、覆盖起止、块号/哈希、分页完整性、计算版本与不可变审核摘要。
- **任务**：工作类型、owner/project、计划 UTC 时间、状态、尝试、租约与目标记录；重复执行以约束和幂等键阻止。
- **运营与用量**：沿用现有项目/行动/日历/社区/请求日志，保留 revision、来源、批准及结果，不另建平行数据孤岛。

禁止新增用户交易私钥表。供应商与 OAuth 凭证继续仅在服务器按最小权限管理，不进入浏览器、源代码、QA 截图或公开仓库。

## 12. 统一界面与信息组织

不重做另一套桌面，也不把每项增强做成独立应用。延续已有四个主要区域：

- **Workbench**：真实工作摘要、待处理事项、已观察变化、下一步；无项目用户能理解功能并开始操作。
- **Launchpad**：项目资料、协议配置、收入去向与签名前审核。分账预览留在发币上下文。
- **Projects**：单项目 Overview、Content、Community、Treasury 与 AI 设置；不另造并列“收入项目”。
- **Market**：发现、Token 详情、交易、X-Ray/研究、关系图与相关 Signals；工具可直接定位具体对象。

点击业务按钮替换主窗口内容，MATE 保留在右侧；小范围确认用对话框。返回路径、已选项目、输入草稿、滚动位置、运行状态和焦点需要有一致策略。手机将 MATE 变为可访问抽屉，不挤压主内容。

延续石墨黑、冷白、银色与品牌黄绿。图表和关系图服务于数据；没有真实数据时使用明确的示例预览或有行动入口的空状态，不伪造在线用户、资金、收益、风险分或交易。

保留现有 5.5 秒可跳过入场及减少动态效果支持；新增动作使用短、可打断反馈。交易时间不可预测，不播放假进度或成功动画冒充确认。

## 13. 发布验收与证据记录

每个小版本记录：提交号、变更范围、执行命令、结果、浏览器尺寸、截图、外部依赖、尚未验证的部分。验收材料存内部文档/忽略的 QA 目录，不作为产品首页内容。

| 检查 | 执行方式与界限 |
| --- | --- |
| 编译与自动化 | 在正式发布快照执行 `pnpm check`；合约变更执行适用的 `pnpm contracts:test`。不能把失败或未运行写成通过。 |
| 协议读验证 | 适用时运行 `pnpm verify:mainnet`，只读主网；记录部署代码/费用/权限变化，不把一次读取当成永久有效。 |
| 本地资金闭环 | 在本地 Anvil 主网分叉执行 `pnpm verify:fork`；不接受远程签名节点，不使用用户私钥，不把结果称为真人主网验收。 |

## 14. 第一批实施任务

下一轮开发从小而完整的切片开始：

1. 建立正式发布快照与核心路径验收表，先复现当前行为；保留未跟踪试验文件，不发布其编译依赖。
2. 优先修正持币分配的样本名称、分母、覆盖字段和确认文案，并补对应算法/界面测试。
3. 完成首次使用 → 无项目 MATE → 建立项目 → 创建私人行动 → 记录结果 → 再次复盘的本地演示，修复所有阻断和重复执行问题。
4. 对 RPC/Blockscout 的历史、分页、固定区块和 trace 能力做有上限的只读探测，形成能力表，再确定 B/D 的实现范围。
5. 交付首个可恢复的事件索引切片及其覆盖展示，再扩展资金关系图；生产准备按 E 并行，尚不公开上线。
